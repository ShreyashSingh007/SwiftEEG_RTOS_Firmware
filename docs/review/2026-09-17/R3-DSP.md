### R3-DSP-01 [high] Stream decoder hands out a payload pointer that consume() overwrites before the caller reads it (CRC-verified header, unverified payload)
- Category: bug | security
- Where: src/proto/proto.c:226-235 (try_extract) with proto.c:184-185 (consume) and proto.c:129 (proto_decode); consumers src/transport/command.c:643-655 and 666-673
- Evidence: `const int err = proto_decode(st->buf, st->need, out);` sets `out->payload = payload_len ? &src[PROTO_HEADER_LEN] : NULL;` (i.e. `&st->buf[8]`), then immediately `consume(st, used);` which does `memmove(st->buf, &st->buf[count], remaining);` before `return true;`. The header comment says the payload is valid "until the next push or poll", but it is clobbered inside the same call.
- Failure scenario: only bites when bytes are already buffered behind the frame, i.e. after resync() re-anchors inside a buffer that holds a complete frame plus >8 more bytes. That is exactly what a truncated/dropped frame produces: a cut frame's declared length swallows the following frames, the CRC fails, resync() lands on the next real SOF with several frames behind it. On BLE the 1024-byte ring drops bytes when the command thread is busy (command.c:607-610, e.g. during a ~1 s rate restart or a 500 ms submit timeout while a host keeps uploading 186-byte SET_FILTER frames). The first frame decoded after the resync is then handed to handle() with its own len/type but payload bytes from the NEXT frame (buf[8..] now holds old buf[8+need..]): a different opcode/arguments run (e.g. a SET_CAR frame executes as SET_CHANNEL args), the reply carries the wrong opcode, and the command that was actually sent gets no reply. Every frame extracted from that buffer except the last is affected. The same codec is intended as the shared host library; on a host decoding a DATA stream after any USB/BLE byte loss this would silently deliver another frame's samples under a valid CRC.
- Why tests miss it: tests/proto/src/main.c:176-193 (truncated frame) checks only `f.seq` and `f.len`, not the payload, and re-sends the SAME frame three times, so the overwriting bytes are identical to the overwritten ones; test_stream_poll_drains_buffered_frames (196-226) also never compares payload.
- Confidence: confirmed-by-reading, and reproduced with a line-by-line Python transliteration (R3-DSP-work/proto_consume_repro.py): an 8-section SET_FILTER cut to 30 bytes, followed by SET_CAR, SET_NOTCH, SET_CHANNEL, PING and 12 READ_REG frames -> 1 CRC error, then 10 frames CORRUPTED. SET_CAR (seq 11) reached handle() as `0c320c` (a short SET_NOTCH), SET_NOTCH (seq 12) as `0aff1800` = SET_CHANNEL all channels gain 24, mux 0, SRB2 off - a register write the host never sent - and SET_CHANNEL (seq 13) as a PING.
- Fix sketch: in try_extract copy the verified frame out (or decode into a separate caller-owned buffer) before consume(), or defer the memmove to the start of the next push/poll (keep a `pending_consume` count). Add a test: truncated frame, then two DIFFERENT good frames, compare payloads.

### R3-DSP-02 [medium] CMD_SET_RATE answers OK before the rate is validated or applied
- Category: contract-drift | robustness
- Where: src/transport/command.c:373-389; src/pipeline/pipeline.c:871-906
- Evidence: `respond(op, CMD_OK, NULL, 0);` then `(void)pipeline_set_rate(sps); return;` - pipeline_set_rate returns -EINVAL for any rate not in rate_code_for() and a negative error when both restarts fail.
- Failure scenario: host sends SET_RATE 300 (or 0, or a restart that fails twice because the AFE is not answering) -> gets CMD_OK; the device keeps the old rate (or is left stopped, `running == false`). This breaks the header contract "so the host can tell rejected from lost" (command.h:7-8); the host's rate-change state machine only learns by polling GET_INFO/GET_CONFIG. In the double-failure case pipeline_start() has already written `sample_rate_hz` (pipeline.c:615-622) so GET_INFO reports the new rate although no stream runs, and SET_FILTER (designed_for check, command.c:268) accepts sections for a rate the AFE is not running.
- Confidence: confirmed-by-reading
- Fix sketch: validate `sps` (expose rate_code_for) and reply EBADARG before restarting; send an EVT (or a second RSP-like status) when the restart itself fails, and only update `sample_rate_hz` once the AFE accepted the rate.

### R3-DSP-03 [high] Any central can set 2-16 kSPS; a DSP thread that falls behind never blocks and starves the command, Bluetooth host and TX threads - no way back but a power cycle
- Category: robustness | performance | security
- Where: src/transport/command.c:373-388; src/pipeline/pipeline.c:725-736 (rate_code_for accepts 2000/4000/8000/16000), 525-541 (drain loop), 441-517 (process); src/transport/stream.c:231; src/transport/ble.c:109 (`BT_GATT_PERM_WRITE`, no encryption/pairing); build/zephyr/.config: `CONFIG_BT_RX_PRIO=8`, `CONFIG_BT_HCI_TX_PRIO=7`, `CONFIG_BT_CTLR_SDC_RX_PRIO=6`
- Evidence: `while ((rf = spsc_peek(&raw_ring)) != NULL) { process(rf); spsc_release(&raw_ring); }` - the thread only sleeps in `k_sem_take(&frame_ready, K_MSEC(100))` when the ring is empty; nothing in process() blocks (`k_msgq_put(&tx_queue, &tx, K_NO_WAIT)`, timebase_now_us() is a spinlock + register read). DSP priority 2 is above stream TX (4), command (6), SDC RX (6), HCI TX (7) and BT host RX (8). SET_RATE has no link or budget check.
- Cost arithmetic (not measured on target): README:945 puts the tracker's ~22 float ops at 2.6 us, i.e. ~0.1 us per float op with its loads/stores. One SVF section per channel is 17 float ops (dsp.c:176-183), ~1.8 us. Default chain = notch + harmonic x 8 ch = 16 evaluations, ~30-40 us a sample with tracker, DC, decode and sink, against a 62.5 us period at 16 kSPS (plus the SPIM END ISR every sample). With host stages of 8 + 8 sections (allowed, command.c:256) it is 144 evaluations, ~270 us a sample: saturated at 4 kSPS and above. On top of that the DATA frame CRC also runs on this thread (stream.c:269-335 sink -> flush() -> proto_encode -> bitwise proto_crc16, see R3-DSP-12): ~64 CRC'd bytes a sample in RAW_UV at ~55-60 instructions a byte is ~60-80 us a sample, so 16 kSPS is saturated even with the default chain and no host sections.
- Failure scenario: a central (or the app's rate-change flow, which re-sends the filters right after the rate change, README:1004-1006) selects 4-16 kSPS with a loaded chain -> the ring overflows continuously, the DSP thread runs 100 % at priority 2, the command thread never runs again (no reply, a SET_RATE back to 250 is never read), ATT writes and notifications stop in the host stack, the stream stops. No watchdog exists (no wdt use in src/ or prj.conf), no button - the device needs a power cycle.
- Confidence: likely (starvation mechanism confirmed by reading; the per-sample cost is estimated, not measured)
- Fix sketch: refuse rates above 1 kSPS on BLE and gate higher USB rates on a cost budget (sections x channels x fs, measured dsp_mean_us); when behind, process a bounded batch and `k_sleep(K_TICKS(1))` (counting the resulting drops) so lower threads run; add a task watchdog fed by the command thread.

### R3-DSP-04 [medium] Input changes that step the signal (mux, test signal, power-down at unchanged gain) neither re-prime the DC estimate nor raise SETTLING
- Category: bug | contract-drift
- Where: src/pipeline/chain.c:190-204; src/pipeline/pipeline.c:329-340 and 353-358; src/transport/command.c:320-341 (TEST_SIGNAL), 356-371 (SET_INPUT), 391-404 (SET_CHANNEL); src/afe/ads1299.c:579 (set_input forces every channel to gain 24)
- Evidence: the only re-prime is `if (lsb != c->lsb_uv[ch]) { c->lsb_uv[ch] = lsb; dsp_dc_init(&c->dc[ch], c->dc[ch].shift); }`. REQ_GAINS changes the mains mask when the mux changed but never re-primes and leaves `restarted` false, so `arm_settling()` is not called. The comment at chain.h:107-111 gives the reason a gain change must re-prime ("carrying the old estimate over would put a step the size of the offset into the filters") - the same holds when the mux switches between electrode, shorted and test signal, or a channel is powered up/down at unchanged gain.
- Failure scenario: channel at gain 24 on a dry electrode with a 100 mV offset; SET_INPUT test signal (or back to normal after a check). The DC estimator (tau = 2^shift samples = 2.05 s at 250/500/1000 SPS) sees a -100 mV step, so the uV stream carries a 100 mV exponential that takes ~10 s to fall to 1 %, through the pre stage, notch and post stage, spread to every channel by the common average at 1/n (12.5 mV on the others with 8 in the mask), with SETTLING clear - contradicting "Samples inside a filter's settling time carry the protocol's SETTLING flag" (README:890-891). (A real gain change is handled: the driver wraps register access in SDATAC/STOP ... RDATAC/START, ads1299.c:479-514, so the first frame after the write - the one the re-prime uses - comes from restarted conversions.)
- Confidence: confirmed-by-reading
- Fix sketch: pass the full CHnSET per channel in REQ_GAINS; for any channel whose gain, mux or power-down bit changed, re-prime its DC estimate (the cascades can keep state, since the re-primed DC output starts at 0) and arm settling for the DC time constant or flag those samples.

### R3-DSP-05 [medium] float32 SVF error grows with residual drift and with rate: 0.7 uV RMS at 1 kSPS and 9 uV RMS at 16 kSPS on 30 mV of drift
- Category: robustness | contract-drift
- Where: src/dsp/dsp.c:146-187; claims at src/dsp/dsp.h:69-77 and README.md:899-908 (measured only on 3 mV at <= 1 kSPS)
- Evidence: the high-pass keeps the drift in its low-pass integrator (`st->ic2 = 2.0f * v2 - st->ic2;`) and moves it by `r->a3 * v3` with a3 = g^2 ~ 1e-7 at 0.1 Hz/1 kSPS and 4e-10 at 16 kSPS, so float32 rounding scales with |ic2| x eps / g. Line-for-line transliteration (R3-DSP-work/svf_f32_rates.py; float32 vs float64, same g/k, 4th-order Butterworth 0.1 Hz, drift at 0.3 Hz which the 0.08 Hz DC removal passes, 20 uV at 10 Hz): 1 kSPS 0.070 uV RMS on 3 mV (matches README's 0.08) but 0.70 uV RMS / 1.0 uV peak on 30 mV; 4 kSPS 0.25 / 2.4 uV RMS; 16 kSPS 0.90 / 9.1 uV RMS, 13 uV peak.
- Failure scenario: dry electrodes (30-190 mV offsets and moving) leave tens of mV of sub-Hz drift after the first-order 0.08 Hz DC removal; at the rates in use the device's drift cut adds up to ~1 uV of drift-correlated error (marginal for single-trial ERP work), and at the 2-16 kSPS rates the firmware accepts and the plan targets for USB the error is EEG-sized.
- Confidence: confirmed (host float32 transliteration; target may differ slightly through FMA contraction)
- Fix sketch: carry the high-pass's low-pass state in int64 fixed point (as the DC stage does) or float64 for sections with g below ~1e-3; or refuse/decimate sub-Hz sections above 1 kSPS; state the drift-amplitude dependence in the README table.

### R3-DSP-06 [low] Section validation passes huge-but-finite values; one non-finite channel spreads through the common average and survives every keep-state retune
- Category: robustness
- Where: src/dsp/dsp.c:68-74, 102-104; src/pipeline/chain.c:74-92, 137-142, 165-170; src/pipeline/pipeline.c:258-259
- Evidence: validity is only `isfinite(...) && s->g > 0.0f && s->k > 0.0f` - NaN/Inf coefficients are refused (tests/dsp/src/main.c:116-130), but m0 = 1e30, or g large enough that `1.0f + s.g * (s.g + s.k)` overflows (a1 = a2 = a3 = 0, leaving `st->ic1 = 2.0f * v1 - st->ic1` an undamped sign flip), or g >= ~4096 (a3 rounds to 1.0, an undamped Nyquist mode) all load. chain_process() has no finite check; the average does `sum += v[ch]` then `v[ch] -= mean` for all 8 channels; retunes keep state (`dsp_cascade_retune` never clears it) and the tracker retunes the notch in place indefinitely (`aim_notch(true, NULL)`).
- Failure scenario: a buggy or hostile upload (or a frame garbled by R3-DSP-01) with a finite 1e30 mix drives a channel to Inf; with the average on, every channel becomes NaN from that sample; re-sending a correct stage with keep-state set, or any mains re-aim, leaves the NaN states in place - only CMD_RESET_CHAIN, a section-count change or a rate change clears them. The raw counts and the tracker (fed pre-filter uV) are unaffected, so it is limited to the uV stream. "With g and k positive a section is stable whatever its mix, so the device can check what it is sent" (README:921-923) is true in exact arithmetic only.
- Confidence: confirmed-by-reading
- Fix sketch: bound |m0|,|m1|,|m2| (e.g. <= 1e3) and g (e.g. <= 1e3, i.e. fc below ~0.4999 fs) and k (>= 1e-4) in dsp_section_is_valid; in chain_process, if a channel's output is not finite, reset that channel's states and flag the sample.

### R3-DSP-07 [low] SET_CHANNEL gain and mux bytes are masked, not range-checked: reserved gain code 7 is written, the chain cannot follow, the error comes after the write
- Category: robustness | contract-drift
- Where: src/transport/command.c:391-404; src/afe/ads1299.c:743-746; src/pipeline/pipeline.c:565-571, 329-335; doc src/transport/command.h:23-24 ("[2]=gain")
- Evidence: `((gain & 0x07u) << 4)` - CHnSET code 7 is "do not use" on the ADS1299 and values >= 8 alias (a gain VALUE of 24 becomes code 0, gain 1). `gain_from_chset` maps code 7 to 0, `chain_set_gain(&chain, ch, 0)` returns -EINVAL, so that channel keeps its previous LSB while the other channels are updated.
- Failure scenario: a central (not the shipped app, which sends codes via GAIN_CODES, tools/swifteeg_link.py:70) sends gain byte 7 or 24: the register is written, the reply is EFAILED (7) or OK with gain 1 (24), and for code 7 the device's uV for that channel is scaled for a gain the PGA is not at. The header's "[2]=gain" does not say it is a code.
- Confidence: confirmed-by-reading
- Fix sketch: reject gain codes > 6 and mux > 7 with EBADARG in command.c before touching the AFE; document "[2]=gain code 0-6".

### R3-DSP-08 [low] Group delay is not reported, and the only implementation is float32 finite differencing that is wrong at the low frequencies ERP work needs
- Category: contract-drift | test-gap
- Where: src/dsp/dsp.c:276-329 (only caller: tests/dsp/src/main.c:375); README.md:1076-1078 ("It is not yet reported in the stream"); owner goal 2 in the brief ("reported group delay")
- Evidence: `const float dw = 1e-4f;` with `phase[i] = atan2f(ni, nr) - atan2f(di, dr);` - near DC the numerator/denominator real parts cancel in float32. Transliteration against the exact float64 group delay (R3-DSP-work/gd_f32.py), 4th-order 0.1 Hz Butterworth high-pass sections: at 1 kSPS, 0.5 Hz, Q 0.54: 139.7 vs 115.6 samples (24 ms out), Q 1.31: 65.0 vs 53.6 (11 ms); at 16 kSPS it returns -309 and -8595 samples at 0.5 Hz (exact +1850, +858) and is still 4-14 ms out at 1-2 Hz. The fixed first-order 0.08 Hz DC stage alone delays 12 ms at 1 Hz and 129 ms at 0.3 Hz and appears nowhere a host can read. The ztest checks only a 40 Hz low-pass at 10 Hz for "finite, > 0, < 100".
- Failure scenario: a host (or the future shared library) that uses this helper to move ERP timestamps for the device's uV stream corrects by the wrong amount by tens of ms for slow components; today nothing reports the delay at all, so the goal is unmet.
- Confidence: confirmed (transliteration)
- Fix sketch: compute analytically in double, tau = Re(sum n b_n z^-n / sum b_n z^-n) for numerator minus denominator, in the shared host core; have GET_CONFIG report the DC shift so the host can include the DC stage.

### R3-DSP-10 [low] Settling estimate ignores bilinear warping: at 250 SPS the default notch is flagged for 94 samples but rings for ~143
- Category: bug | contract-drift
- Where: src/dsp/dsp.c:195-211; used by src/pipeline/pipeline.c:195-201
- Evidence: `: 1.0f / (g * k);` - the decay of the analogue prototype. The digital pole radius is sqrt(d2) with d2 = (1 - gk + g^2)/(1 + gk + g^2) (the same d2 as dsp.c:293), so tau = -2/ln(d2) ~ (1 + g^2)/(g k): the code is short by (1 + g^2), which is 1.53 for 50 Hz and 10.5 for the 100 Hz harmonic at 250 SPS (g = 0.7265, 3.078), 1.28 for a 40 Hz low-pass at 250 SPS, ~1 for 0.1 Hz high-passes.
- Measured with the device's loop (R3-DSP-work/settle_check.py; primed restart vs the same filter running for 20 s, 50 uV mains + 10 uV harmonic + 10.3 Hz, worst phase): 250 SPS 50 Hz Q12 + harmonic flagged 94, transient above 1 % of its peak until sample 143; 250 SPS 60 Hz flagged 59, until 117. 500 and 1000 SPS are conservative (246 vs 190, 519 vs 360), because the sum over sections over-counts.
- Failure scenario: after a rate change to 250 SPS, CMD_RESET_CHAIN or any stage restart, SETTLING clears 200-230 ms before the notch has rung down, so a few uV of mains-frequency ringing is delivered as signal - against "Samples inside that window are flagged, so a transient is never mistaken for signal" (dsp.h:151-155).
- Confidence: confirmed (simulation of the same loop)
- Fix sketch: `tau = -2.0f / log(d2)` (or (1 + g*g)/(g*k)) for the underdamped branch, and the matching warped form for the overdamped one; mirror in dsp_ref.settle_samples.

### R3-DSP-12 [medium] Bitwise CRC-16 on the DSP thread: ~60-80 us a sample in RAW_UV, a hard ceiling on the sample rate
- Category: performance
- Where: src/proto/proto.c:18-34; called per DATA frame from the DSP thread via src/transport/stream.c:256 (flush) <- stream_on_sample, the pipeline sink (src/main.c:263)
- Evidence: `for (int b = 0; b < 8; b++) { if (crc & 0x8000u) { crc = (uint16_t)((crc << 1) ^ 0x1021u); } else { crc = (uint16_t)(crc << 1); } }` - eight test/shift/xor/zero-extend/branch iterations a byte, ~55-60 Thumb-2 instructions a byte. A frame covers 7 header bytes + payload: RAW_UV 16 + 3 x 56 = 191 bytes for 3 samples (~64 a sample), UV_F32 215 for 6 (~36), RAW_I24 167 for 6 (~28).
- Failure scenario: at 64 MHz that is roughly 60-80 us of CRC per RAW_UV sample (the encoding the app uses with device filters on, README:865-868): ~6-8 % of the CPU at 1 kSPS, and by itself more than the whole CPU at 16 kSPS (~1-1.3 s of work a second) - so the 16 kSPS USB mode the plan targets cannot be reached whatever the filters, and it feeds the starvation in R3-DSP-03. Estimate from instruction counts, not measured.
- Confidence: likely
- Fix sketch: table-driven CRC-16/CCITT-FALSE (256 x uint16 = 512 B flash, ~8 instructions a byte, same check value 0x29B1) or a 16-entry nibble table; keep the golden check-value test. Longer term, move framing off the DSP thread (TX thread) so a slow link or encoder cannot delay sampling.
