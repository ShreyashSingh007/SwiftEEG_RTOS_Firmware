## Findings

### R4-HOST-01 [medium] FrameParser trusts an unvalidated length: one false SOF swallows up to 65 KB (USB)
- Category: robustness
- Where: tools/swifteeg_link.py:280-300 (FrameParser.feed); decode checks at tools/proto_ref.py:80-89 run only after the wait
- Evidence: `length = struct.unpack_from("<H", self.buf, 4)[0]` / `total = proto_ref.HEADER_LEN + length + proto_ref.CRC_LEN` / `if len(self.buf) < total: return out` / `raw = bytes(self.buf[:total]); del self.buf[:total]` then `except Exception: self.bad += 1`. Version, type and `MAX_PAYLOAD` (1024) are checked only inside `proto_ref.decode`, after the parser has already waited for and then thrown away the whole claimed length. On failure it discards `total` bytes, not 1.
- Failure scenario (measured with crafted streams, R4-HOST-work/parser_test*.py, RAW_UV 194-B frames): length field 0xFFFF -> 338 frames lost (~1 s at 1 kSPS, ~4 s at 250 SPS); a single stray 0xA5 byte -> 243 frames lost; 7 bytes missing inside one frame -> 148 lost. Opening the USB port on a device that is already streaming (app crash/restart, port reopen; `usb.c` keeps the partly sent ring) starts mid-frame; 32 % of frames contain an 0xA5 after the SOF, so over 400 random start points the parser lost mean 35 frames, p90 180, max 577, >100 frames in 12.5 % of starts. Any RSP in that window (the connect-time GET_CONFIG, see app findings) is swallowed with it. BLE is mostly immune because `_take_notification` clears the buffer after every notification (swifteeg_link.py:457-459). The firmware writes whole frames only (usb.c:213-216), so steady-state USB is fine; the exposure is start-up and any future transport that can slip bytes.
- Confidence: confirmed-by-reading + measured
- Fix sketch: after 8 header bytes, reject `ver != 1`, unknown type or `len > MAX_PAYLOAD` by dropping ONE byte and rescanning; on CRC failure also drop one byte, not `total`. Same test with that parser: 0 frames lost in all 400 starts, 1 frame for the 0xFFFF and 7-byte cases, 0 for the stray 0xA5.

### R4-HOST-02 [high] Recording header is written once; rate, gain or input changes mid-recording silently mis-describe the raw data, and key metadata is never recorded
- Category: bug (data integrity)
- Where: tools/swifteeg_app.py:905-910 (header), 810-816 (_set_gain), 636-680 (_set_rate), 803-808 (_set_source), 1112-1134 (config reply overwrites rate/gain), 1209-1213 (rows)
- Evidence: header row `["# SwiftEEG raw counts", f"rate={self.rate}", f"gain={self.gain}", f"lsb_uv={link.lsb_uv(self.gain):.9f}"]` is written only in `_toggle_record`. `_set_gain` does `self.gain = int(self.gain_var.get())` and sends SET_CHANNEL; `_set_rate` restarts acquisition; neither checks `self.recorder` nor writes a marker row. Rows carry only `[ts_us, seq, ch1..ch8]` counts. `self.gain = cfg["gains"][0] or 24` keeps channel 1's gain only.
- Failure scenario: start recording at gain 24, switch to gain 12 to get an electrode off the rail: every later row is at twice the LSB but the file still says `lsb_uv=0.022351741`, so re-analysis silently halves those microvolts. A rate change mid-file makes `rate=` wrong and restarts `seq` with no marker. Pressing Record before the first GET_CONFIG reply writes the app default `rate=250 gain=24` whatever the device is set to. A "Shorted (noise)" or "Test signal" input, bias/lead-off state (lead-off injects DC current), per-channel gains, encoding, firmware/app version, host wall-clock at the first sample (needed to align stimulus markers) and the filter settings in force are not in either file, so a recording cannot be re-analysed exactly, which is the stated purpose (raw data for ERP / deep learning).
- Confidence: confirmed-by-reading
- Fix sketch: write a full JSON sidecar (device config reply verbatim + decoded, app/firmware version, host UTC at first sample, per-channel gain/mux) at start; on any config-changing command while recording either refuse it or close the segment and start a new file/segment with a fresh header (or write an inline `# config` marker row with the sample seq it applies from).

### R4-HOST-03 [high] Acquisition losses are invisible in recordings: `seq` stays unbroken, the CSV drops the OVERRUN flag, and no one checks `ts_us` continuity
- Category: bug (timing integrity)
- Where: tools/swifteeg_app.py:1026-1039 (gap/lost accounting), 1209-1213 (CSV rows), 1391-1393 (banner); firmware contract src/pipeline/pipeline.c:455-487, src/transport/stream.c:329
- Evidence: firmware `.seq = st_seq++` per processed sample; ring drops only set `out.flags |= EEG_FLAG_OVERRUN` ("a frame that never reached this function never took a sequence number, so the numbering stays unbroken across it and only the hardware timestamps show the hole", pipeline.c:473-480); a bad-status frame does `st_seq--` with no flag at all (pipeline.c:467-470). Host: `if f.flags & link.FLAG_OVERRUN: self.lost += 1`; rows are `[round(ts0 + i * period_us), seq0 + i, *row.tolist()]` with no flags column; banner `samples lost on the device ({self.lost} times)`.
- Failure scenario: a DSP-thread stall like 2026-09-16 (107 samples lost in 20 s at 1 kSPS) or an SPI status glitch: the CSV's `seq` runs on without a hole and nothing in the row marks the spot. Epoching by `seq / rate` (the usual method, and the only one if `ts_us` is not checked) shifts every later stimulus-locked epoch by the lost samples (107 ms after that 20 s) and silently smears an ERP average. The UI reports "N times", never how many samples, and a bad-status drop is not reported at all. TX-queue drops, by contrast, do leave a `seq` gap, so the two loss types need different checks and the host implements only one.
- Confidence: confirmed-by-reading
- Fix sketch: host: expected_ts = prev_ts0 + prev_count * period (0.13 % drift is ~5 us per batch); a larger jump = round(dt/period) missing samples -> count them, add a `flags`/`missing_before` column or a gap-marker row. Firmware (shared contract): number samples by DRDY count so `seq` gaps are the single continuity signal.

### R4-HOST-04 [medium] BleLink shutdown: the STREAM_STOP sent by Reset/exit is never written, and close() is ignored during scan/connect
- Category: race
- Where: tools/swifteeg_link.py:400-446 (_thread/_main loop), 461-466 (send/close); callers tools/swifteeg_app.py:700-708 (_reset_link), 1736-1747 (_close); firmware src/transport/ble.c:204-223
- Evidence: callers do `self.link.send(link.CMD_STREAM_STOP)` then `self.link.close()`; `close()` only sets `_stop`; the loop `while not self._stop.is_set() and not dropped.is_set():` checks the flag before draining `_out`, so the queued frame is discarded. `_stop` is not checked between `find_device_by_name(..., timeout=20.0)` and `BleakClient(...)`, and nothing joins the thread. Firmware `disconnected()` clears subscriptions but never calls `stream_enable(false)`.
- Failure scenario: measured with a fake bleak module (R4-HOST-work/ble_close_test.py): STREAM_STOP queued then close() was written in 0/100 trials. So after Reset or closing the app over BLE the device keeps streaming; the next BLE connect delivers data while the button says "Start streaming", and the next USB connect opens mid-frame (R4-HOST-01). close() during a scan still connected 0.44 s later and then disconnected; Disconnect then Connect inside the scan window ran two BLE threads at once (both alive), which on WinRT means two GATT sessions to one device (effect on the second session speculative). `_close` then destroys the window after 200 ms while a daemon thread may still be inside disconnect.
- Confidence: confirmed-by-reading + simulated (WinRT consequences speculative)
- Fix sketch: in the loop, drain `_out` before honouring `_stop`; check `_stop` after scan and after connect; `close(timeout)` joins the thread; the app waits for the join (off the UI thread) before destroy. Consider firmware stopping the stream on disconnect.

### R4-HOST-05 [medium] One exception in the pump throws away the whole drained batch, repeats every refresh, and is reported only on stderr
- Category: robustness
- Where: tools/swifteeg_app.py:941-962 (_frame try/except), 1005-1059 (_pump locals), 1196-1213 (_consume writes before plotting), 884-893 (stop recording)
- Evidence: `block_raw = []` / `imu_raw = []` are locals filled from the queue; `_consume(block_raw)` runs after the loop; `except Exception: ... traceback.print_exc()` at most every 2 s; `self.samples += len(counts)` is before the CSV loop, `_ring_write` and `_note_arrival` after it.
- Failure scenario: disk full, a removed USB stick or a cloud-sync lock makes `writerow` raise OSError. Every later pump raises at the first row, so each drained batch is lost for both file and plot, indefinitely. The EEG trace freezes, the stats line switches to "plot idle - no data arriving" while the SPS counter keeps climbing, the recording silently stops growing, and the only report is a traceback on a console that a double-click launch does not have. The same happens if closing the file raises in `_toggle_record` (state stays "recording" into a closed file -> ValueError each frame). Any malformed DATA frame shorter than 16 bytes (`DATA_HDR.unpack_from`, swifteeg_link.py:147) also discards the batch it arrived with.
- Confidence: confirmed-by-reading
- Fix sketch: catch per frame inside the drain loop; isolate recording errors (stop recording, keep plotting, show a red status); record errors in the UI, not stderr; length-check payloads in decode_data.

### R4-HOST-06 [medium] A dropped link looks like success: green status, no reconnect, and the UI, recording and device state go stale
- Category: robustness
- Where: tools/swifteeg_app.py:988-1003 (_pump status/connection), 540-562 (_toggle_conn); tools/swifteeg_link.py:444-446
- Evidence: link posts `"BLE link dropped"`; app colours `"#ff6b6b" if "fail" in msg or "not found" in msg else "#5ed18b"` -> green. On `not self.link.connected` the app only sets `self._was_connected = False`; the Connect button keeps saying "Disconnect", the stream button "Stop streaming", the recorder stays open with no marker; there is no reconnect attempt.
- Failure scenario: headset out of range or brown-out during a long recording: the status turns green "BLE link dropped", the plot goes idle, the files stay open. After a manual Disconnect/Connect the new samples append to the same CSV; if the device reset, `seq` and `ts_us` restart mid-file with no marker. With the owner's attention profile a green message during a session is the failure most likely to be missed.
- Confidence: confirmed-by-reading
- Fix sketch: an explicit link-state enum from the link (connecting/connected/lost) instead of string matching; red, persistent "link lost" banner; auto-reconnect with backoff; on reconnect write a segment marker (or start a new file) and re-sync stream/button state from GET_CONFIG.

### R4-HOST-07 [medium] The app times and filters samples by a rate it never confirmed: one-shot connect GET_CONFIG, ignored device rates, and a give-up path that resumes anyway
- Category: bug (timing)
- Where: tools/swifteeg_app.py:985-992 (connect GET_CONFIG, no timeout), 1112-1119 (`if sps in (250, 500, 1000)`), 682-698 (give-up), 1208-1212 (row time from `self.rate`), 540-549 (USB Disconnect sends no STREAM_STOP); firmware src/pipeline/pipeline.c:725-736 accepts 250..16000
- Evidence: `if self.link.connected and not self._was_connected: ... self._send(link.CMD_GET_CONFIG)` is sent once, with no timer or retry (only a rate change has `_rate_change_overdue`). `sps = cfg["rate"]; if sps in (250, 500, 1000): ... self.rate = sps`, but the status still prints `f"connected - {sps} SPS"`. On give-up: `self._rate_change = None; if change["resume"]: self._begin_stream()` with `self.rate` still the unconfirmed new value. Rows: `period_us = 1e6 / self.rate` -> `round(ts0 + i * period_us)`.
- Failure scenario: (a) USB reconnect to a device still streaming (Disconnect does not stop it, and neither does a BLE exit, R4-HOST-04): measured with realistic RAW_I24 streams, the parser (R4-HOST-01) swallows the single config reply in 10 % of connects (500 trials each at 250 and 1000 SPS, reply 30 or 100 ms after open). A fresh app then stays at its defaults (250 SPS, gain 24). (b) The device is at 2000-16000 SPS, set by another host or a USB test: the reply is ignored and the status says "connected - 2000 SPS" while the app runs at 250. In both cases, with the device at 1000 SPS and the app at 250, rows 1-5 of every 6-sample batch are stamped 3-15 ms late, the header says `rate=250`, and the host filters are designed for the wrong fs (a "50 Hz" notch sits at 200 Hz). Nothing turns red.
- Confidence: confirmed-by-reading + measured (a); (b) confirmed-by-reading
- Fix sketch: connect state "unsynchronised" until a config reply arrives (timeout + retry, block Record meanwhile); accept any rate the device reports (or refuse to stream and say so); measure the period from consecutive batch `ts0`/`seq` and flag a >2 % mismatch with `self.rate`; derive within-batch row times from that measurement, not the nominal rate.
